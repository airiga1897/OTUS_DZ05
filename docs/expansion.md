# Эксплуатация, расширение и временные испытания

## Этапы

| Этап | Реализация | Ответственность |
| --- | --- | --- |
| Инфраструктура | [infrastructure.py](../scripts/infrastructure.py), Terraform | План, проверка допустимых действий, apply |
| Настройка | [ansible/site.yml](../ansible/site.yml), [ansible_configuration.py](../scripts/ansible_configuration.py) | Роли common, mysql_member, mysql_cluster, mysql_router, django_portal |
| Начальные данные | [initialize_portal](../app/knowledge/management/commands/initialize_portal.py) | Однократный loaddata и маркер в БД одной транзакцией |
| Проверки | [verify.py](../scripts/verify.py) | Django-тесты, HTTP, CRUD, отказ и восстановление |
| Повторное применение | [growth.py](../scripts/growth.py) | Сохранение идентичности и данных при добавлении узлов |
| Временная приёмка | [test_cycle.py](../scripts/test_cycle.py) | Изолированный сценарий с удалением собственного стенда |

Внешние команды остаются deploy, verify, open и destroy. Проверки приложения
не запускаются внутри скрипта установки сервисов. Проверка данных и состояния
кластера до/после изменения является обязательной защитой повторного deploy.

## Добавление узла

Поддерживаются одна app и от трёх до девяти БД db1–db9 с уникальными адресами.
Начальная конфигурация содержит три БД. Четыре участника требуют большинства
из трёх и не увеличивают допустимое число отказов относительно трёх участников;
для увеличения устойчивости предпочтительно нечётное число участников.
[AdminAPI addInstance](https://dev.mysql.com/doc/mysql-shell/8.0/en/add-instances-cluster.html)
проверяет совместимость версии и присоединяет участника через распределённое восстановление.

Для согласованного живого испытания на действующем исправном стенде:

1. Сохранить отдельную резервную копию БД и media. Приостановить пользовательские
   изменения на время сравнения снимков; чтение портала может продолжаться.
2. Создать пользовательскую статью и изображение, изменить исходную статью.
   Повторить deploy с неизменённой конфигурацией, проверить сохранение данных.
3. В `.local/lab-config.json` добавить в nodes один свободный узел, например
   `"db4": {"host": 24, "role": "db"}`. Не менять существующие параметры.
4. Выполнить обычный `lab.py deploy`. Он использует сохранённое размещение,
   проверяет квоты, а затем разрешает в плане только port, boot volume и VM
   нового узла и no-op для существующих ресурсов. Смена пула здесь запрещена.
5. Новый пустой сервер присоединяется через clone. На существующие участники
   clone не запускается; непустой приёмник отклоняется. Уже присоединённый
   участник не добавляется повторно. Полный отказ кластера автоматически
   не переинициализируется.
6. Проверить `docs/expansion-latest.json`: сохранены ID всех прежних ресурсов,
   адрес приложения, все Django-строки и media; участники ONLINE, реплики
   согласованы, HTTP и CRUD работают. Снимки содержат хеши, а не содержимое данных.
7. Ещё раз выполнить deploy без изменения nodes: нет новых ресурсов и
   повторного add_instance. Затем при необходимости выполнить verify и open.

Настройка существующих БД не переустанавливает пакеты и не перезапускает MySQL.
Router использует метаданные кластера; его повторный bootstrap не требуется.
Приложение повторно применяет сервисную конфигурацию и миграции, но не загружает
фикстуру. Если маркера в БД на существующем стенде ещё нет, данные принимаются
без перезаписи; даже пустая существующая БД не заполняется заново автоматически.
Обновление сервисов приложения может кратко прервать его доступность.

При ошибке state, расширенный контекст, исходный снимок и ключи сохраняются.
Частично созданные ресурсы учитываются Terraform; повтор deploy продолжает
тот же состав. Не редактировать состав незавершённой операции. Destroy всего
стенда выполняется только отдельной командой. Уменьшение состава, замена ВМ,
изменение профиля и перенос размещения требуют отдельного сценария.

## Временный цикл

`lab.py test-cycle` разрешён только без стенда, контекста, непустого state
и незавершённой операции. Он захватывает локальную блокировку `.test-cycle.lock`
и связывает каждый создаваемый контекст с уникальным test_run_id.

Цикл проверяет исходное развёртывание и отказы, создаёт контрольную статью с
реальным файлом media, повторяет deploy, добавляет один узел, проверяет
сохранение данных и ID, штатное состояние и CRUD, повторяет расширенный deploy.
В finally destroy допускается только при совпадении test_run_id контекста.
Подбор другого пула разрешён лишь после подтверждения очистки своей неудачной
попытки; для действующего стенда автоматического переноса нет.

После подтверждённой очистки исходная конфигурация восстанавливается;
credentials остаются для отдельного удаления. При ошибке очистки сохраняются
контекст, state, ключи, текущая конфигурация и блокировка. Не удалять блокировку
для обхода защиты: сначала подтвердить удаление через state/API и разобрать
незавершённую операцию. Итог — `docs/cycle-latest.json`.

## Ansible в обычном deploy

Настройка обязательно выполняется через реализованные Ansible-роли.
Linux-контроллер находится на существующей app; прямой SSH к БД использует
ключ, временно переданный в защищённый каталог контроллера. Bootstrap Python
готовит только среду управления; пакеты, конфигурации и сервисы применяет
Ansible. [Подготовка, роли и границы проверок](ansible.md).

Terraform и проверки остаются самостоятельными этапами. Наличие ролей
не доказывает безопасность clone или сохранность данных и не заменяет испытание.

## Критерий готовности

Локальные mock-тесты проверяют план, добавление и повтор AdminAPI, сохранность
контрольных данных, ошибку настройки и повтор, отказ от чужого test-cycle.
Они не подтверждают работу расширения в облаке. Сохранённые прежние отчёты
проверяют базовый стенд, а не новый сценарий.

Готовность расширения подтверждается только согласованным живым test-cycle
с успешными расширением, повторным deploy, сохранностью данных/media и
последующим аудитом удаления. До такого прогона облачная приёмка расширения
остаётся открытой. Автоматически запускать её по результатам mock-тестов нельзя.
