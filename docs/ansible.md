# Ansible: среда управления и настройка

## Подготовка

Локально из PowerShell выполнить `scripts/setup.ps1`: он создаёт собственные
инструменты и проверяет YAML/Jinja-исходники. Эти проверки не запускают серверы.

В обычном deploy после Terraform контроллер автоматически готовится на
существующей app: Ubuntu 24.04, Python 3.12, собственный venv
`/home/otus/.ansible-dz05/venv`, ansible-core 2.20.10. Дополнительная ВМ
не создаётся. На рабочем месте не нужны Docker или WSL: нативный Windows
не используется как control node. [Поддержка control node](https://docs.ansible.com/projects/ansible/latest/intro_installation.html).

[bootstrap-ansible.sh](../scripts/bootstrap-ansible.sh) ждёт cloud-init,
проверяет ОС и Python, устанавливает только python3-venv/openssh-client,
создаёт venv и устанавливает зафиксированный Ansible. Требуется доступ app
к репозиториям Ubuntu и PyPI. Версия контроллера проверяется перед playbook.
Это воспроизводимая автоматическая часть подготовки, отдельной ручной
настройки контроллера после создания ВМ не требуется.

## Этапы playbook

| Роль | Реализованная настройка |
| --- | --- |
| common | cloud-init, проверка входных данных, пакеты, защищённая конфигурация инструментов |
| mysql_member | Шаблон MySQL, стабильный server_id, перезапуск при изменении, AdminAPI account новых узлов |
| mysql_cluster | Проверенная процедура AdminAPI, добавление только пустых новых узлов, запрет повторного bootstrap действующего кластера |
| mysql_router | Сервисный пользователь, однократный bootstrap, systemd и ожидание порта |
| django_portal | Исходники, venv/pip, конфигурации, миграции, транзакционная начальная загрузка, static, uWSGI/Nginx |

Конфигурации и сервисы применяются builtin-модулями и handlers. MySQL Shell
остаётся специализированным инструментом AdminAPI с защитой непустого
приёмника; [cluster.py](../scripts/cluster.py) вызывается задачей роли.
Альтернативного пути настройки через прежние node.py/app.py нет.
Повторная настройка не загружает фикстуру заново и не пересоздаёт ВМ.

## Доступ и временные данные

Python получает host keys из доверенной Nova-консоли. Ansible использует
StrictHostKeyChecking и этот known_hosts. App управляется локальным соединением,
БД — по приватным адресам TCP/22. На app передаётся только временный SSH-ключ
стенда, inventory и секреты приложения; реквизиты оператора Selectel туда
не передаются. Каталог запуска имеет mode 0700, ключ и vars — 0600.

После успеха или ошибки временный каталог контроллера удаляется в finally.
При недоступности SSH удаление не гарантируется; сохраняется ошибка для
диагностики. Постоянный root-only /root/dz05.json остаётся для проверок;
удаление ВМ уничтожает и его. Локальные state, ключи и диагностика не удаляются
при ошибке роли. Полный destroy очищает их после аудита state/API.
Operator.json и конфигурация повторного запуска сохраняются.

## Проверки

```powershell
.\.tools\venv\Scripts\python.exe scripts/check_ansible.py
.\.tools\venv\Scripts\python.exe -m unittest discover -s tests -p 'test_*.py'
```

На Windows проверены YAML/Jinja, генерация inventory, обязательный вызов
ansible-playbook и удаление временного ключа при mock-ошибке. Linux syntax-check
выполняется на app перед применением ролей. Его прохождение и реальное
применение текущих ролей ещё требуют согласованного облачного испытания.
Критерий готовности — [живой цикл добавления узла](expansion.md), а не наличие
playbook или успешные mock-тесты.
