# Загрузка начальных данных

Начальные данные подготовлены по материалам ДЗ04 и загружаются Django-фикстурой.
[initial_data.json](../app/knowledge/fixtures/initial_data.json) хранится в репозитории
и содержит пять статей с PK 1–5: четыре материала ДЗ04 и описание ДЗ05.
Первые четыре статьи соответствуют исходным материалам; updated_at фиксирован для воспроизводимости, это не историческое
время изменения записей. Исходные статьи не содержат media.

## Порядок загрузки

Сценарий настройки приложения выполняет на ВМ через MySQL Router:

```bash
python manage.py migrate --noinput
python manage.py initialize_portal --allow-initial-load
```

Схема MySQL создаётся только миграциями Django. Фикстура включена в архив
приложения; отдельная исходная БД и экспорт при deploy не требуются.
Команда initialize_portal загружает фикстуру через loaddata и записывает
постоянный маркер knowledge_initialdataimport одной транзакцией. При ошибке
откатываются и строки, и маркер. Повторная настройка читает маркер из БД,
а не с диска приложения; удаление файлов приложения не запускает повторный импорт.

--allow-initial-load передаётся только при первом развёртывании. Если в БД
уже есть статьи, отсутствие маркера означает принятие существующих данных
без загрузки фикстуры и перезаписи. На действующем стенде команда без этого
ключа сохраняет даже намеренно пустую БД. Старый файл imported удаляется
Ansible только после успешной фиксации маркера в БД.

## Идентификаторы, связи и права

Фикстура содержит только knowledge.article: пользователей, паролей, sessions,
contenttypes и permissions в ней нет. Contenttypes и стандартные права создаёт
migrate. Проверки подтверждают четыре права Article, связи user/group/permission,
сохранение PK и всех полей статей, отсутствие дублей при повторной загрузке.
У Article нет внешних ключей; связи системы авторизации проверяются отдельно.

На MySQL вставка явных PK должна продвигать AUTO_INCREMENT. verify проверяет
следующий идентификатор и совпадение данных с фикстурой. Локальные Django-тесты
используют SQLite в памяти только как тестовый backend; проверку MySQL они
не заменяют. При deploy SQLite не используется.

Media хранится на ВМ приложения отдельно от MySQL. Создание статьи через admin,
загрузка и чтение нового изображения проверяются в verify.
