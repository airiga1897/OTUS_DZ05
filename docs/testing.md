# План испытаний живого стенда

Сценарий выполнен на двух независимых развёртываниях. Фактические результаты,
времена и ограничения приведены в [results.md](results.md). Ниже порядок повторения.

1. Зафиксировать версии Server/Shell/Router, dba.getCluster().status({extended:1}),
   три ONLINE, один PRIMARY, два SECONDARY. Проверить InnoDB и PK всех таблиц Django.
2. migrate через Router 6446; импорт фикстуры и отдельное восстановление media.
   Сверить число статей, пользователей, memberships и permissions с источником.
   Проверить создание записи с PK выше импортированного максимума.
3. Через HTTP проверить главную, detail, readiness, статику; через admin по SSH-туннелю
   создать/обновить/прочитать статью и загрузить изображение. Выполнить verify_database.
4. Запустить непрерывные HTTP-запросы и CRUD-пробы, сохранять timestamp и результат.
   Определить текущий PRIMARY из метаданных, не предполагать, что это db1.
5. Выключить только этот узел ДЗ05 по UUID из собственного Terraform output.
   Зафиксировать время отказа и появления нового PRIMARY, ошибки и восстановление
   HTTP/CRUD через неизменный Router endpoint. Два оставшихся узла должны быть ONLINE.
   Проверить наличие записей, зафиксированных до отказа, и новых записей после него.
6. Включить тот же UUID в finally. Дождаться ONLINE, при необходимости rejoinInstance.
   Сверить данные на трёх узлах и повторить CRUD. Повторить для одного SECONDARY.
7. Зафиксировать итоговый статус и все ошибки. Обезличить адреса/UUID/имена пользователей
   перед публикацией; не публиковать fixture, stdout с секретами или полный state.

Не выполнять forceQuorumUsingPartitionOf и rebootClusterFromCompleteOutage в обычном
испытании одного отказа. Потеря двух из трёх узлов означает потерю кворума и блокировку
записи. ВМ приложения/Router и её media — единые точки отказа вне области HA базы.
Успешный terraform validate и тесты SQLite не заменяют перечисленные проверки.
