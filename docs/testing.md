# Проверка приложения и отказоустойчивости

## Условия запуска

Проверки выполняются на развёрнутом стенде после APPLICATION READY.
На локальном компьютере Windows в PowerShell, из корня репозитория:

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py verify
```

Нужны сохранённые credentials оператора, собственные state, SSH-ключ,
known_hosts и .local/lab.json от текущего deploy. Их подготавливают сценарии
[развёртывания](operations.md). verify рассчитан на четыре исходные статьи;
пользовательские материалы до проверки добавлять не следует.
Сценарий оставляет инфраструктуру работающей.

## Выполняемые проверки

| Проверка | Действие сценария | Ожидаемый результат |
| --- | --- | --- |
| Исходные данные | Сравнить все поля статей с импортированной фикстурой, создать запись | Четыре исходные статьи совпали, новый PK выше импортированных |
| Права Django | Создать временного редактора и группу с правами Article | Работают contenttypes, permissions и связи user/group |
| Admin и media | Войти, создать статью с изображением через HTTP внутри SSH-туннеля | Создание успешно, статья и изображение читаются, байты изображения совпали |
| HTTP и БД | Проверить главную, статью, readiness, CSS и CRUD через Router | HTTP 200, запись и чтение успешны |
| Отказ PRIMARY | Определить текущий PRIMARY, проверить имя и UUID своей ВМ, выполнить Nova os-stop | Два узла ONLINE, выбран один PRIMARY, работают HTTP и запись через прежний Router |
| Возврат узла | Выполнить os-start в finally, дождаться присоединения | Три узла ONLINE, сохранены подтверждённые записи |
| Отказ SECONDARY | Повторить остановку и возврат узла с ролью SECONDARY | Запись на оставшихся узлах и восстановление трёх ONLINE |
| Сверка реплик | Проверить InnoDB, наличие первичных ключей и SHA256 всех полей статей | Все таблицы InnoDB с PK, статьи одинаковы на трёх репликах |
| Уборка данных | Удалить временные статьи, редактора и группу | Остались четыре исходные статьи |

CRUD означает создание, чтение, изменение и удаление записи; PK — первичный ключ.
Во время смены PRIMARY возможен краткий HTTP 503; сценарий фиксирует ответы
и подтверждает восстановление работы. Каждый выключенный узел запускается
в finally, после чего проверяется его ONLINE. Потеря двух узлов лишает
кластер большинства; испытание выключает узлы строго по одному.

## Получение результата

Ожидается LIVE VERIFICATION PASSED и success=true в новом отчёте:

```powershell
$reportFile = Get-ChildItem .\docs\verification-*.json | Sort-Object Name | Select-Object -Last 1
$report = Get-Content $reportFile.FullName -Raw | ConvertFrom-Json
$report.success
$report.failures | Select-Object stopped_role, node, surviving_members, recovered_members
$report.replica_snapshots
$report.final_cleanup
```

При ошибке сценарий возвращает ненулевой код. Отчёт сохраняет выполненные
проверки и success=false; такой запуск не считается успешной проверкой.
Фактически подтверждённое поведение приведено в [результатах](results.md).
После проверки выполнить отдельное [удаление по шагу 7 инструкции](operations.md),
в том числе при ошибке. Успешные validate и SQLite-тесты подтверждают только
соответствующие локальные проверки, а не работу кластера.
